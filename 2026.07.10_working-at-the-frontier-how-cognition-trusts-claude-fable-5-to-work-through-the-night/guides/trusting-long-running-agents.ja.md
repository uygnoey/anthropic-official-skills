# Cognition はエージェントを走らせっぱなしにしてよいとどう判断するか

Cognition はシリコンバレーの基準で見ても若い会社だ。自律型 AI ソフトウェアエンジニアである Devin を
2024年初頭に作った。エージェントの基本的な仕組みがようやく成立するかどうかという時期である。

Devin はエンジニアがいつまでも手をつけられない仕事を引き受ける。コードベースの移行、たまったバグ、
先延ばしにされ続ける機能。顧客は急成長スタートアップから Fortune 500 企業まで幅があり、要求水準は高い。
Devin が書いたコードは信頼でき、本番投入できるものでなければならない。静かに紛れ込んだ小さなバグ一つが、
下流で本物の問題を引き起こしうるからだ。

研究担当 SVP の Silas Alberti は Devin を支えるモデルの訓練とテストを担い、初期からほぼすべての Claude
世代を動かしてきた。

## 「我々はいかなる eval も信じない」

Alberti は最初の本当の飛躍を 2024年末の Claude 3.6 Sonnet に見ている。ツールを確実に連鎖させ、複数
ステップのタスクを保持できた最初のモデルだった。チームがそれを Devin に組み込むと、社内利用は 3 倍に
なった。

その履歴が彼を容易には感心しない人物にしている。Cognition は、モデルがベンチマークを制した直後に自社の
エンジニアが使い始めた途端に崩れる場面を見てきた。「こういう形で何度も痛い目を見てきました」と Alberti
は言う。だからチームはどんなスコアよりも自社のエンジニアを信じる。最も審美眼のある開発者たちが新しい
モデルを実際の一日分の仕事に投入し、基準はそのコードを本当に残したいと思えるかどうかだ。

Alberti の言い方を借りれば、「我々はいかなる eval も信じない」。

これは測定を避けるという話ではなく、何を証拠と見なすかのルールである。Cognition 自身もベンチマークを
運用している。

## 以前のモデルが突き当たった限界

それだけの進歩があってなお、天井が一つ残っていた。エージェントが筋を見失うまでにどれだけ長く走れるか、
である。

> 「Fable 以前は、数分、せいぜい一時間くらいタスクに留まれるエージェントに任せる、という感じでした。」

それを過ぎるとセッションは漂流した。以前のモデルに五つの案を同時に検討させると、把握しきれずに混乱した。
あるデータベース移行では、以前の Opus モデルが技術的には仕事を終わらせたものの、その過程で微妙なバグを
次々と埋め込んでいた。成功を報告してしまう分、最も高くつく失敗だ。

インシデントのトリアージも同じ形をしていた。以前のモデルは該当する一行まで掘り下げず、ログの表面に
留まりがちで、しかも何があっても答えを出すよう訓練されていた。だから「最初に見つけたもっともらしいこと
を自信たっぷりに主張して、そこで止まる」。エンジニアたちはそれを聞き流すことを覚えた。

この最後の一文が本当のコストである。無視される出力は、たまに正しくても価値を生まない。

## Cognition 自身の基準を超える

Cognition は Frontier Code というベンチマークでモデルを採点する。既存のベンチマークが、テストは通っても
実際のコードベースでは生き残らないコードに報酬を与え続けたために、自前で作ったものだ。Alberti はこれを
「アンチスロップ（anti-slop）」基準と呼ぶ。

その最難関サブセットで、以前の Opus モデルは約 10% だった。Claude Fable 5 は約 30% を記録した。

チームの最初の反応は疑いだった。「バグじゃないか。こんなはずがない。」通常、ベンチマークの跳ね上がりには、
そのモデルが実務で本当に優れているのかをめぐる数週間の議論がついてくる。今回はドッグフーディングが数字と
一致した。

> 「正直、ちょっとした衝撃でした。」

スコアとドッグフーディングが一致することは、どちらか一方だけよりはるかに強い結果だ。そして記事自身が
述べるとおり、その一致こそが異例の部分である。

## 何が変わったのか — ホライズン

> 「我々が気づいた最大のことはホライズン、つまりどれだけ長く自立していられるかでした。もう寝ようという
> ときに『よし、これを続けてくれ。俺が起きるまで止まるな』と言ったタスクが何度かあります。そして起きて
> みると、8 時間ぶっ通しで作業し、実際に本物の進捗を出していた。そんなものは見たことがありませんでした。」

両方の半分が等しく重要だ。8 時間はホライズンであり、*実際に本物の進捗*はかつての長時間実行が失敗して
いた部分である。エージェントはタスクに留まらないまま、いくらでも忙しくしていられるからだ。

記事はホライズンが保たれた理由を三つ挙げる。

**雑然とした文脈でも頭が冴えていた。** Cognition の社内デバッグツールをきちんと使いこなした最初のモデル
だった。ブラウザでログを繰りながら、ノイズの中から結論を引き出した。貼り付けられたものしか読めない
エージェントは、あなたの集中力の長さが上限になる。

**実行前に不変条件を宣言した。** 以前のモデルがつまずいた移行作業で、このモデルは自らに課す不変条件を
まず述べ、それに沿って実行した。無人の長時間実行において、不変条件はあなたの監督の代わりを果たす。
そして走り出す前にそれを読むほうが、8 時間分の diff を読むよりはるかに安い。

**知らないことを知らないと言った。** トリアージで根本原因を突き止めると同時に、自分が確立できていない
範囲を明示した。Alberti はまさにそこが信頼を実際に回復させる部分だと言う。境界が示された答えは、どこを
検証すべきかを教えてくれる。境界のない自信満々の答えは全部を検証させ、それは結局自分でトリアージするの
と同じことだ。

## 次に来るもの

Cognition の創業時の賭けは、エージェントはクラウドで何時間も走るべきだ、というものだった。会社の最初の
一年、モデルはそこに届いていなかった。

Alberti は、Claude Fable 5 がその賭けの完全版を実行可能にしたと言い、その一部はすでに製品に入っている。
Devin は Slack チャンネルを見張り、タグ付けされなくても課題に飛び込める。本番環境を監視してスパイクを
自力でトリアージすることもできる。そうした仕事をうまくこなしたとき、「チームの本物のエンジニアのように」
感じられると彼は言う。

彼はこれがエンジニアリングチームの既定になると見ている。1〜2 年のうちに、エージェントセッションの 90% は
問題を見つけ、コードベースを走査し、修正案とともに向こうから声をかけてくる能動的なものになるという。

> 「会社でずっと作りたかったことの多くが、いま可能になりました。」
