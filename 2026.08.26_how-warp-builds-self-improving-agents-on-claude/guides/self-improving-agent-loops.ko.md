# 스스로 개선하는 에이전트 루프: Warp의 방식

## 문제

AI 기반 터미널이자 에이전틱 개발 환경인 Warp는, 정확도 80% 수준으로 작업을 수행하는 에이전트가
"시끄럽고 성가신(noisy and annoying)" 사용자 경험을 만든다는 사실을 확인했다. 팀은 자체 내부 코드
리뷰 에이전트에서 이 문제를 직접 겪었다. 엔지니어들이 도움이 되지 않는 코멘트와 낮은 품질의 출력을
보고한 것이다.

뻔한 해결책은 확장되지 않았다. 프롬프트를 손으로 다시 쓰고 `AGENTS.md` 같은 컨텍스트 파일을
개선하는 일은 끝이 없다. 진짜 문제는 한 층 아래에 있었다. **피드백은 보통 세션이 끝나면 사라지고**,
그래서 에이전틱 루프에서 꼭 필요한 컨텍스트가 빠져버린다는 점이다.

## 프레임워크

Warp의 해법은 **스킬(skills)** — 지식을 파일로 인코딩한 것 — 위에 세워져 있으며, 두 개의 구성
요소와 그 사이에 있는 사람으로 이루어진다.

### 이너/베이스 스킬 (Inner / base skill)

기능적 도메인 지식과 지시문을 담는다. 코드 리뷰의 경우, PR이 열릴 때 실행되어 리뷰를 만들어낸다.

### 사람의 피드백

가장 중요한 재료다. 명시적인 피드백이 가장 잘 작동한다. 무엇이 잘못됐는지뿐 아니라 *왜* 잘못됐는지
설명하는 피드백이다. Warp의 CEO Zach Lloyd의 표현대로, 사람이 "이건 좋고 유용한 코멘트였다"라고
확인해 줄 수도 있지만, "우리 코드베이스 컨벤션상 이런 종류의 전역 변수는 이런 네이밍 맥락을
따른다" 같은 구체적인 이유야말로 에이전트에게 개선 방법을 알려준다.

### 아우터/개선 스킬 (Outer / improver skill)

작업마다가 아니라 **일정에 따라(on a schedule)** 실행되는 관찰자 에이전트다. 축적된 사람의 피드백을
끌어와, 에이전트의 제안과 사람의 반응을 비교하고, 베이스 스킬에 대한 작고 초점이 분명한 수정을
제안한다.

스킬은 평범한 파일이기 때문에, 에이전트는 사실상 리뷰하고 승인하고 머지할 수 있는 PR 워크플로를
통해 스킬을 갱신하게 된다. 사람이 머지하지 않으면 실행 중인 시스템은 아무것도 바뀌지 않는다.

## 스스로 개선하는 스킬을 쓰는 법

- **규칙이 아니라 원칙을 써라.** 컴퓨터를 프로그래밍하듯이가 아니라, 똑똑한 사람에게 지시하듯이
  구성하라. "반복되는 코드를 찾아라"가 변수 네이밍 규칙을 빠짐없이 나열한 것보다 낫다.
- **이유를 설명하라.** 근거가 있으면 에이전트가 경직된 지시를 따르는 대신 문제를 스스로 추론할 수
  있고, 일반화가 좋아진다.
- **피드백을 주기 쉽게 만들어라.** 사람들이 이미 일하는 곳 — PR이나 이슈의 코멘트 — 에서 추가 제출
  단계 없이 자동으로 수집하라. 마찰이 낮아야 신호가 계속 흐른다. 어렵게 만들면 피드백이 끊기고,
  개선도 함께 멈춘다.
- **스킬은 작게 유지하고 점진적 공개(progressive disclosure)를 써라.** 좋은 스킬 파일은 모든 것을
  한 번에 컨텍스트에 쏟아붓는 대신 리소스 파일과 스크립트를 참조한다.
- **피드백의 질이 양보다 중요하지만, 양도 도움이 된다.** 시니어 엔지니어의 상세하고 도메인 특화된
  피드백이 대충 남긴 피드백보다 낫다. 에이전트가 달리 알 방법이 없는 도메인 지식을 담고 있다면
  표본이 적어도 아주 좋은 신호가 된다.
- **개선 스킬에 더 많은 공을 들여라.** 개선 스킬은 여러 용도에 걸쳐 재사용성이 매우 높기 때문에
  투자한 만큼 돌려받는다.

## 실제 루프: 이슈 트리아지

Warp의 [이슈 트리아지 에이전트](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage)가
이 프레임워크를 처음부터 끝까지 보여준다.

1. 누군가 GitHub 이슈를 등록하면 GitHub Action이 에이전트를 트리거한다. 에이전트는 복잡도와
   실현 가능성을 분석하고, 라벨을 붙이고, 수정 방향을 제안한다.
2. 어떤 샘플 이슈에서 이너 스킬은 잘 동작했지만 `ready to spec` 라벨을 놓쳤다. 기여자가 제품 및
   기술 스펙을 직접 만들어도 된다는 신호를 주는 라벨이다.
3. 메인테이너가 이슈에 직접 피드백을 남기며 기대치와 그 근거를 함께 설명했다.
4. Warp의 오케스트레이션 플랫폼 Oz에서 "update triage"라는 예약 에이전트로 실행되는 아우터 개선
   스킬이 GitHub에 인증하고, 번들된 Python 스크립트를 실행해 피드백이 달린 최근 이슈들을 가져오고,
   결과를 JSON으로 요약한 뒤 구체적인 신호를 식별했다.
5. 그리고 피드백을 담아내는 가장 작은 수정을 제안했다. UI/UX 세부가 정의되지 않았더라도 이슈가 실제
   문제를 서술하고 있다면 `ready to spec`을 적용하라는 것이다.
6. 이 갱신은 표준 코드 리뷰 절차를 거쳤다. PR에는 어떤 신호가 어떤 변경을 이끌었는지 설명이 담겼다.
   사람의 승인 후 머지된 변경은 다음 트리아지 실행이 물려받는 지식이 되었다.

Warp는 지금 오픈소스 리포지토리 전반에서 이 패턴을 운영한다. 스펙 작성, 리뷰, 트리아지 에이전트가
각각 별도로 있고, 각자 자기 개선 루프를 가지고 있다.

## 확장하기 전에 답해야 할 질문들

**스킬과 메모리를 혼동하고 있지 않은가?** 스킬은 절차적이고 안정적이다. "X를 어떻게 하는가"이며,
실행에 무관하고, 의도적으로 변경된다. 메모리는 추론 시점에 에이전트가 자동으로 쓰며 끊임없이
바뀐다.

**개선 루프는 하나면 되는가, 에이전트마다 하나씩인가?** 중간에서 만나라. 템플릿화된 베이스 루프가
에이전트 간의 공통 부분을 담고, 그 위에 도메인 특화된 가중치를 얹는다. 에이전트가 몇 개뿐이라면
각자 개선 루프를 가져도 되지만, 백 개라면 공유해야 한다.

**피드백이 틀렸을 때는 어떻게 되는가?** 틀릴 것이라고 가정하라. 에이전트가 피드백을 맹목적으로
받아들이게 두지 말고, 검증할 수 있는 컨텍스트를 주고, 누구의 의견을 반영할지 걸러내고, 필터링
단계나 최종 리뷰 단계에 사람을 남겨두라.

**당신의 도메인은 검증 가능한가?** 검증 하네스를 먼저 만들고 나서 에이전트가 그에 맞춰 튜닝하게
하라. 참조 코퍼스를 생성하고, 출력을 참조와 비교하고, 고치고, 반복한다.

**검증 가능하지 않다면?** 골든 출력에 대한 결정론적 평가가 존재하는 곳에서는 그것에 기대라. 사람의
피드백이 꼭 필요한 곳이라면 도메인 전문가로 제한하라. 문을 활짝 열지 마라.

**시스템 전체가 나아지고 있는지 어떻게 아는가?** 사람이 이미 보고 있는 전역 지표 — 머지까지 걸리는
시간, 기여자 수, 비용 — 를 추적해 개선 에이전트에 다시 넣어라. 배포는 기어가기 → 걷기 → 뛰기 순으로
점진적으로 진행하라.

## Warp에 대하여

2020년 CEO Zach Lloyd가 창업. 스택은 Rust, Golang, GitHub Actions, Oz라는 사내 에이전트
오케스트레이션 플랫폼, 그리고 Claude Platform. 7,300만 달러 투자 유치, 월 80만 개발자 사용,
Fortune 500의 56%가 사용, 현재까지 Warp 내부에서 실행된 Claude Code 세션 1,000만 건(주당 40만 건
이상), Warp Agent 대화 누적 4,000만 건.
