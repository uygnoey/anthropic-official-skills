# 自己改善するエージェントループ：Warp のやり方

## 課題

AI を活用したターミナルであり、エージェンティックな開発環境でもある Warp は、80% の精度でタスクを
実行するエージェントが「うるさく、煩わしい（noisy and annoying）」ユーザー体験を生むことを突き止め
た。チームは自社の社内コードレビューエージェントでこの問題に直面した。エンジニアから、役に立たない
コメントと低品質な出力が報告されたのだ。

分かりやすい対処法はスケールしなかった。プロンプトを手で書き直し、`AGENTS.md` のようなコンテキスト
ファイルを改善し続ける作業は終わらない。本当の問題はもう一段下にある。**フィードバックはセッション
が終わると消えてしまう**ため、エージェンティックループから不可欠なコンテキストが失われるのだ。

## フレームワーク

Warp の解決策は **スキル（skills）**——知識をファイルにエンコードしたもの——の上に築かれており、
2 つの構成要素と、その間に立つ人間から成る。

### インナー／ベーススキル

機能的なドメイン知識と指示を保持する。コードレビューであれば、PR が開かれたときに実行されてレビュー
を生成する。

### 人間のフィードバック

決定的に重要な要素。明示的なフィードバックが最も効く。何が間違っていたかだけでなく、*なぜ* 間違って
いたかを説明するものだ。Warp CEO の Zach Lloyd はこう述べる——人間が「これは良くて有用なコメントだっ
た」と認めることもできるが、「うちのコードベースの慣習では、この種のグローバル変数はこの命名文脈を
使う」といった詳細な理由こそが、エージェントに改善の仕方を伝える。

### アウター／改善スキル

タスクごとではなく **スケジュールに従って** 実行されるオブザーバーエージェント。蓄積された人間の
フィードバックを取得し、エージェントの提案と人間の反応を突き合わせ、ベーススキルへの小さく焦点の
絞られた編集を提案する。

スキルはただのファイルなので、エージェントは実質的に、レビューでき、承認でき、マージできる PR ワーク
フローを通じてスキルを更新することになる。人間がマージしない限り、稼働中のシステムは何も変わらない。

## 自己改善するスキルの書き方

- **ルールではなく原則を書く。** コンピュータをプログラミングするのではなく、賢い人に指示するつもりで
  構成する。「繰り返されているコードを探せ」のほうが、変数命名規則を網羅した一覧より良い指針になる。
- **理由を説明する。** 根拠があれば、エージェントは硬直した指示に従うのではなく問題を推論でき、汎化
  が改善する。
- **フィードバックを出す手間をゼロにする。** 人がすでに作業している場所——PR や issue への直接の
  コメント——で、追加の提出ステップなしに自動で拾う。摩擦が低いことがシグナルを流し続ける。難しく
  すればフィードバックは止まり、改善も止まる。
- **スキルは小さく保ち、段階的開示を使う。** 良いスキルファイルは、すべてを一度にコンテキストへ流し
  込むのではなく、リソースファイルやスクリプトを参照する。
- **フィードバックは量より質。ただし量も効く。** シニアエンジニアによる詳細でドメイン特化した
  フィードバックは、ざっくりしたものより価値が高い。エージェントが他に知りようのないドメイン知識を
  含んでいれば、サンプル数が少なくても非常に良いシグナルが得られる。
- **改善スキルには余分に手をかける。** 改善スキルはユースケースをまたいで高い再利用性を持つため、
  投資は繰り返し報われる。

## 実際のループ：issue トリアージ

Warp の [issue トリアージエージェント](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage)
が、このフレームワークを端から端まで示している。

1. 誰かが GitHub issue を立てると、GitHub Action がエージェントを起動する。エージェントは複雑さと
   実現可能性を分析し、ラベルを付け、修正の方向性を提案する。
2. あるサンプル issue では、インナースキルはうまく動いたものの `ready to spec` ラベルを見落とした。
   コントリビューターがプロダクト仕様と技術仕様を自分で作ってよい、というシグナルを与えるラベルだ。
3. メンテナーが issue に直接フィードバックを残し、期待値とその根拠の両方を説明した。
4. Warp のオーケストレーションプラットフォーム Oz 上で「update triage」というスケジュール実行の
   エージェントとして動くアウター改善スキルが、GitHub に認証し、同梱の Python スクリプトを実行して
   フィードバックの付いた最近の issue を取得し、結果を JSON に要約し、具体的なシグナルを特定した。
5. そしてフィードバックを取り込む最小の編集を提案した。UI/UX の詳細が未定義であっても、issue が実在
   する問題を記述しているなら `ready to spec` を適用する、というものだ。
6. この更新は標準のコードレビューを通った。PR にはどのシグナルがどの変更を促したかの説明が添えられて
   いた。人間の承認を経てマージされた変更は、次のトリアージ実行が引き継ぐ知識になった。

Warp は現在、オープンソースリポジトリ全体でこのパターンを運用している。仕様作成、レビュー、トリアー
ジのエージェントがそれぞれ独立して存在し、いずれも自己改善ループを備えている。

## スケールする前に答えるべき問い

**スキルとメモリを混同していないか。** スキルは手続き的で安定している——「X のやり方」であり、実行に
依存せず、意図的に変更される。メモリは推論時にエージェントが自動的に書き込み、絶えず変化する。

**改善ループは 1 つか、エージェントごとに 1 つか。** 中間を取る。テンプレート化されたベースループが
エージェント間の重なりを捉え、その上にドメイン固有の重み付けを載せる。エージェントが数個ならそれぞれ
が改善ループを持ってよいが、100 個なら共有すべきだ。

**フィードバックが間違っていたら。** 間違っていると想定せよ。エージェントに鵜呑みにさせず、妥当性を
確かめるためのコンテキストを与え、誰の意見を採用するかをフィルタし、フィルタ段階か最終レビュー段階、
あるいはその両方に人間を残す。

**そのドメインは検証可能か。** まず検証ハーネスを作り、それに対してエージェントをチューニングさせる。
参照コーパスを生成し、出力を参照と比較し、修正し、繰り返す。

**検証可能でない場合は。** ゴールデン出力に対する決定論的な評価が存在するところではそれに頼る。人間
のフィードバックが必要な場面では、ドメイン専門家に限定する。門戸を開け放ってはいけない。

**システム全体が改善しているとどう分かるか。** 人間がすでに追っているグローバル指標——マージまでの
時間、コントリビューター数、コスト——を追跡し、改善エージェントに戻す。デプロイは、はいはい → 歩く →
走る の順で段階的に進める。

## Warp について

2020 年に CEO の Zach Lloyd が創業。スタックは Rust、Golang、GitHub Actions、Oz という社内エージェント
オーケストレーションプラットフォーム、そして Claude Platform。調達額 7,300 万ドル、月間 80 万人の
開発者が利用、Fortune 500 の 56% が採用、これまでに Warp 内で実行された Claude Code セッションは
1,000 万件（週 40 万件超）、Warp Agent の会話は累計 4,000 万件。
