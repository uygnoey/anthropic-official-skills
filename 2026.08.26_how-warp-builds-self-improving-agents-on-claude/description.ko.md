# Warp는 Claude 위에서 스스로 개선하는 에이전트를 어떻게 만드는가

## 이 글이 뭔가요

고객사 엔지니어링 사례. AI 기반 터미널이자 에이전틱 개발 환경인 Warp는 정확도 80%로 동작하는
에이전트가 "시끄럽고 성가신" 경험을 만든다는 것, 그리고 프롬프트나 `AGENTS.md` 같은 컨텍스트 파일을
손으로 고치는 방식은 해결책으로 확장되지 않는다는 것을 발견했다. 근본 문제는 세션이 끝나면 사람의
피드백이 사라진다는 데 있다.

Warp의 답은 스킬 두 개로 이루어진 루프다. 실제 작업을 수행하는 베이스(이너) 스킬과, 일정에 따라
실행되며 축적된 사람의 피드백을 읽고 베이스 스킬에 대한 작은 수정을 일반 PR로 제안하는
개선(아우터) 스킬이다. 글은 그 루프를 위한 스킬 작성법을 다루고, Warp의 이슈 트리아지 에이전트를
실제 예시로 따라가며, 이 패턴을 확장하기 전에 답해야 할 질문들로 마무리한다.

## 언제 유용한가요

- 당신의 에이전트가 대체로 맞지만 시끄럽고, 매주 프롬프트를 손으로 고쳐 쓰고 있을 때.
- 엔지니어들의 피드백은 있지만 그것을 변경으로 바꿔주는 장치가 없을 때.
- 개선 루프를 몇 개나 둘지 — 에이전트마다 하나인지, 공유 템플릿 하나인지 — 정해야 할 때.
- 에이전트가 그냥 틀린 피드백을 그대로 반영하는 것을 막아야 할 때.
- 당신의 도메인이 검증 하네스를 지원하는지, 지원하지 않으면 무엇을 해야 하는지 알고 싶을 때.

## 핵심 포인트

- **세션이 끝나면 피드백이 사라지는 것이 진짜 버그다.** 프롬프트를 손으로 다시 쓰고 `AGENTS.md`를
  개선하는 방식은 증상만 다루기 때문에 확장되지 않는다.
- **이너/베이스 스킬.** 기능적 도메인 지식과 지시문을 담고 작업에 대해 실행된다. 코드 리뷰라면
  PR이 열릴 때다.
- **아우터/개선 스킬.** 작업마다가 아니라 일정에 따라 실행되는 관찰자다. 축적된 사람의 피드백을
  끌어와, 에이전트의 제안과 사람의 반응을 비교하고, 베이스 스킬에 작고 초점이 분명한 수정을
  제안한다.
- **스킬은 평범한 파일이므로 갱신이 곧 PR이다.** 에이전트는 리뷰·승인·머지가 가능한 워크플로를 통해
  변경을 제안하며, 실제 시스템 변경의 통제권은 사람에게 남는다.
- **규칙이 아니라 원칙을 쓰고, 이유를 설명하라.** 컴퓨터를 프로그래밍하지 말고 똑똑한 사람에게
  지시하라. 근거가 있으면 에이전트가 새로운 상황을 추론할 수 있어 일반화가 좋아진다.
- **피드백을 주기 쉽게 만들어라.** 사람들이 이미 일하는 곳 — PR과 이슈 코멘트 — 에서 자동으로
  수집하라. "마찰이 낮아야 신호가 계속 흐른다."
- **명시적 피드백이 단순한 인정보다 낫다.** "좋고 유용한 코멘트였다"보다, 어떤 컨벤션이 있고 그
  이유가 무엇인지 밝히는 편이 훨씬 강한 신호다.
- **질이 양보다 중요하지만, 양도 도움이 된다.** 시니어 엔지니어의 상세하고 도메인 특화된 피드백은
  표본이 적어도, 에이전트가 달리 얻을 방법이 없는 신호를 담는다.
- **개선 스킬에 더 많이 투자하라.** 여러 용도에 걸쳐 재사용성이 매우 높다.
- **실제 예시.** Warp의 이슈 트리아지 에이전트가 `ready to spec` 라벨을 놓쳤고, 메인테이너가 이슈에
  그 이유를 설명했다. 예약 실행된 개선 스킬이 번들된 Python 스크립트로 최근 피드백을 가져와 JSON으로
  요약하고, 가장 작은 수정을 제안했다 — UI/UX 세부가 미정이어도 실제 문제를 서술한 이슈라면
  `ready to spec`을 적용하라. 이 변경은 리뷰를 거친 PR로 반영됐다.
- **확장 전에 여섯 가지 질문에 답하라.** 스킬 대 메모리, 개선 루프의 개수, 피드백이 틀렸을 때의
  대처, 도메인의 검증 가능성, 검증 불가능할 때의 대안, 그리고 시스템 전체의 개선을 보여주는 전역
  지표.
