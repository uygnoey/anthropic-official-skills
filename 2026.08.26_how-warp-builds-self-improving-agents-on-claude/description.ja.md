# Warp は Claude の上で自己改善するエージェントをどう作っているか

## この記事について

顧客事例のエンジニアリング記事。AI を活用したターミナルであり、エージェンティックな開発環境でもある
Warp は、80% の精度で動くエージェントが「うるさく、煩わしい」体験を生むこと、そしてプロンプトや
`AGENTS.md` のようなコンテキストファイルを手で書き直す方法は解決策としてスケールしないことを突き
止めた。根底にある問題は、セッションが終わると人間のフィードバックが消えてしまうことだ。

Warp の答えは 2 つのスキルから成るループである。実作業を担うベース（インナー）スキルと、スケジュール
に従って実行され、蓄積された人間のフィードバックを読み、ベーススキルへの小さな編集を通常の PR として
提案する改善（アウター）スキルだ。記事はそのループのためのスキルの書き方を扱い、Warp の issue
トリアージエージェントを実例としてたどり、このパターンを拡大する前に答えるべき問いで締めくくる。

## どんなときに役立つか

- 自分のエージェントはおおむね正しいが騒がしく、毎週プロンプトを手で書き直しているとき。
- エンジニアからのフィードバックはあるが、それを変更に変える仕組みがないとき。
- 改善ループをいくつ回すか——エージェントごとに 1 つか、共有テンプレート 1 つか——を決めるとき。
- 単純に間違ったフィードバックにエージェントが従ってしまうのを防ぎたいとき。
- 自分のドメインが検証ハーネスを構築できるか、できない場合はどうするかを知りたいとき。

## 主なポイント

- **セッション終了でフィードバックが消えることこそが真のバグ。** プロンプトを手で書き直し
  `AGENTS.md` を改善する方法は症状を扱っているだけなのでスケールしない。
- **インナー／ベーススキル。** 機能的なドメイン知識と指示を保持し、タスクに対して実行される。コード
  レビューなら PR が開かれたときだ。
- **アウター／改善スキル。** タスクごとではなくスケジュールで動くオブザーバー。蓄積された人間の
  フィードバックを取得し、エージェントの提案と人間の反応を突き合わせ、ベーススキルへの小さく焦点の
  絞られた編集を提案する。
- **スキルはただのファイルなので、更新は PR になる。** エージェントはレビュー・承認・マージ可能な
  ワークフローを通じて変更を提案し、実際のシステム変更の主導権は人間に残る。
- **ルールではなく原則を書き、理由を説明する。** コンピュータをプログラミングするのではなく、賢い人
  に指示する。根拠があれば新しい状況を推論でき、汎化が改善する。
- **フィードバックを出す手間をゼロにする。** 人がすでに作業している場所——PR や issue のコメント——
  で自動的に拾う。「摩擦が低いことがシグナルを流し続ける」。
- **明示的なフィードバックは単なる肯定に勝る。** 「良くて有用なコメントだった」よりも、慣習とその
  理由を述べるほうがはるかに強いシグナルになる。
- **質は量に勝るが、量も効く。** シニアエンジニアによる詳細でドメイン特化したフィードバックは、
  サンプルが少なくても、エージェントが他に得る手段のないシグナルを含む。
- **改善スキルには余分に投資する。** ユースケースをまたいで高い再利用性がある。
- **実例。** Warp のトリアージエージェントが `ready to spec` ラベルを見落とし、メンテナーが issue で
  その理由を説明した。スケジュール実行の改善スキルが同梱の Python スクリプトで最近のフィードバックを
  取得し、JSON に要約し、最小の編集を提案した——UI/UX の詳細が未定義でも実在する問題を記述している
  issue には `ready to spec` を適用する——それがレビュー済みの PR として取り込まれた。
- **拡大する前に 6 つの問いに答える。** スキルとメモリの区別、改善ループは 1 つか複数か、フィード
  バックが間違っていたときの対処、ドメインが検証可能か、検証できないときに何に頼るか、そしてシステム
  全体の改善を示すグローバル指標は何か。
