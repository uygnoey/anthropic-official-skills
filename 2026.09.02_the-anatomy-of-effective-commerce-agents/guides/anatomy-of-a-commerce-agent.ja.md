# 効果的なコマースエージェントの解剖学

小売、マーケットプレイス、旅行、エンターテインメント、通信の各領域でエンタープライズチームと取り組んだ
Anthropic の知見をまとめたガイド。順に四つを扱う。アーキテクチャ、速く安くする方法、本番運用、そして
モデルが変わっても変わらないもの。

## 第 1 部 — アーキテクチャ

### コマースエージェントとは

コマースエージェントはオンラインカタログを通じた売買を簡単にする。消費者向けは検索、比較、代替提案、
注文の組み立てを担う。事業者向けは売上分析、プロモーション、在庫、価格設定を担う。土台を見れば両者は
同じ設計だ。**標準的なエージェントループの中の一つのモデル — 目標について推論し、コンテキストを探索
し、ツールを通じて行動する。**

### サブエージェントではなくスキル

この点についてガイドは明確だ。コマースエージェントをサブエージェントに分解してはいけない。

- コマースの会話は複数の意図と複数ターンにまたがって強く結合している。
- サブエージェント間の受け渡しは状態の喪失を生み、応答品質を下げる。
- 受け渡しごとにトークンコストが倍増し、レイテンシーが加わる。
- コマースのワークフローではドメイン境界がきれいに分かれない。

エージェントスキルは受け渡しのオーバーヘッドなしにモジュール性をもたらす。ガイドの言葉では、スキルを
備えた単一エージェントは *「品質において、一つのプロンプトですべてを賄う設計とサブエージェント設計の
両方を一貫して上回り、しかもタスクあたりのコストとレイテンシーがしばしば低かった」*。

サブエージェントが価値を保つのは二つの場合だけだ。ディープリサーチのような狭く自己完結したタスク、
そして既に独自のコンプライアンス要件をもつ専用エージェントを運用しているドメイン。

### システムプロンプトかスキルか — 頻度で決める

- **システムプロンプト** — ほとんどのターンで必要な内容。目安はトラフィックのおよそ 3 分の 1 以上。
- **スキル** — ロングテールの機能と条件付きの能力。

重要な指示は例外で、頻度によらず常にシステムプロンプトに置く。安全ルール、法的要件、ブランド制約、
ユーザーの安全に関わる事実。

リファレンス実装の分配は次のとおり。

- **ショッピングエージェントのプロンプト:** グラウンディング、カートとチェックアウトのセマンティクス、
  提示ルール、商品検索。
- **ショッピングスキル:** search-discovery、purchase-research、planning-goals、customer-care、
  memory-personalization。
- **マーチャントスキル:** performance-insights、catalog-listings、inventory-operations、
  pricing-promotions、marketing-campaigns。

### ツールの設計

**既存システムの上に築く。** エージェントのツールは、すでに運用しているカタログ、カート、価格、注文の
各システムを呼び出すべきだ。*「それらを再実装してはいけない。ツールの境界こそ、そのロジックが終わり、
モデルの判断が引き継ぐ場所である。」*

**ツールの結果はコンテキストである。** 推論に関係するフィールドだけを返す。*「生のレスポンスはツールの
内部で再構成する。データだけでは次の一手が自明でない場合には、それを付け加えることも含めて。」* エラー
の場合はエラーコードではなく、行動につながる案内を返す。

### UI コンポーネントをツールとして

独自マークアップの代わりに、各 UI コンポーネントをツールにする — `present_products`、
`present_itinerary`。これにより、コンポーネントが messages 配列にネイティブ形式で保存され、型安全性と
検証が得られ、レイアウトが保たれてユーザーが「最初のホテル」「上から三つ目」と言えるようになり、
クライアントへの段階的ストリーミングが可能になる。

トレードオフは、提示ツールの引数がサーバー側でバッファリングされ、体感レイテンシーを悪化させること。
`eager_input_streaming: true` を設定するとスキーマ保証を一部犠牲にトークン単位のストリーミングになる。
ガイドはスキーマ違反が *「Claude Sonnet クラス以上のモデルでは非常にまれ」* だと記している。

## 第 2 部 — 速く、安く

### タスク完了レイテンシー

```
(モデルのターン数 × 最後のトークンまでの時間) + ツール処理時間
```

この形から三つのレバーが導かれる。

1. **ターンを減らす** — 必要になりそうなコンテキストを先に読み込み、より賢いモデルを使い、並列ツール
   呼び出しを有効にする。
2. **ツールを速くする** — バックエンドを最適化し、ツールを先行ディスパッチする。
3. **トークンを速くする** — eval スイープでモデルと設定を選ぶ。

実務としては、ユーザーが来た商品ページやダッシュボードを先に注入する。賢いモデルは複雑なクエリで
ターン数を減らし、それがトークン毎秒の遅さを上回ることが多いと覚えておく。コマースは複数商品の検索、
ポリシー文書の照会、売上データの取得を同時に必要とするので、1 ターンで複数ツールを呼べるようにする。
そして各ツールの引数のストリーミングが終わった時点で実行し、数秒の空白を数百ミリ秒に縮める。

### 体感レイテンシー

実際の所要時間とは別に扱う。

- **コンポーネントを段階的にストリーミングする。** 500〜700 トークンの応答を一塊で返さず、段階的に
  描画する。
- **作業を見せる。** ステップごとの短い進捗行 —「水辺のホテルを探しています」— を、ツール引数から
  組み立てるか、専用の `user_facing_message` パラメーターで受け取る。

### プロンプトキャッシュ

利用できる最大のコスト削減手段。

- キャッシュされた入力の読み出しは新規トークンの 10 分の 1 のコスト。
- キャッシュ書き込みには約 1.25 倍のプレミアムがつくが、2 回目の利用で回収される。
- *「私たちが見てきた最良のコマース導入は 90〜99% のキャッシュヒット率で動いている。」*
- キャッシュされたトークンは 10 万トークン付近でおよそ 1.5〜2 倍の速度向上ももたらす。

変化の頻度順にコンテキストを三つのセグメントに分ける。

1. **グローバル** — システムプロンプトとツール定義。セッション間でバイト単位に同一であること。
2. **セッション** — ユーザーごとのコンテキストと会話履歴。
3. **揮発性** — 現在時刻、現在ページ。必ずセグメントの末尾に置く。

実装上の要点が二つある。スキルはシステムプロンプトへの追記ではなく **ツール結果** として読み込み、
キャッシュされた会話プレフィックスに載せる。キャッシュのブレークポイントは毎ターン前へ送り、
プレフィックスの一致を保つ。そしてページコンテキストのようなシグナルで必要なスキルが分かるなら、先に
注入してスキル読み込みのターンごと省く。

### モデルと設定を選ぶ

1. **指標を定義する** — 品質のしきい値(タスク完了、関連性、グラウンディング)、レイテンシー
   (p50/p99)、コスト予算。
2. **スイープする** — 候補となるモデルと effort レベル全体で eval スイートをフル実行する。
3. **反復する** — プロンプトは特定のモデルに合わせて調整される。大きいモデルが推論で補うことを、
   小さいモデルには明示的に指示する必要がある。
4. **タスクあたりのコストを測る** — 呼び出し単価だけでなく、ターン数と失敗率を織り込む。

> 結果が拮抗していて、コストがタスクあたりの採算とレイテンシーに収まるなら、知能を選べ。

## 第 3 部 — 本番運用

### セッションを越えて残るメモリ

ユーザーがアレルギーや好みといった制約をセッションのたびに言い直す必要はない。

**保存。** メモリはモデルのコンテキストではなく本番データベースに置く。事実は型付きレコードとして
構造化する。key(`shoe_size`、`default_store`)、value、category、source session。

**データの取り扱い。** どの種類のメモリを保持するかを決め、プロンプトではなく書き込み経路の
バリデーターで強制する。保存された事実を閲覧・訂正・削除できるユーザー向けインターフェースを用意する。
好みは古くなるので保持期間を設定する。管轄ごとのコンプライアンスのため、メモリをデプロイ単位の
トグルにする。

**書き込み。** エージェントのツールではなく非同期抽出を使う。*「メモリは非同期に書く……各ターンの
終わり、あるいは数ターンごとに……別スレッドまたは別プロセスのエージェントが会話を読み、事実を作成・
更新・削除する。」* これによりレイテンシーのオーバーヘッドが消え、社内 eval では事実の再現率が 13%
高くなり、エージェントの推論から判断の負荷が外れる。抽出プロンプトはユーザーとアシスタントのテキスト
だけを読み、ツール結果は決して読まない。さもないと商品説明がユーザーの事実になってしまう。

**読み出し — 三層。**

1. **常にコンテキストに** — ほぼすべてのリクエストで必要な固定の事実。既定の店舗、受け取り方法の好み。
2. **ターンごとにプリフェッチ** — 現在のリクエストのシグナルによって関連性が生じた事実。
3. **ルックアップツール** — それ以外すべて。明示的な取得の背後に置く。

### 安全性: 強制はハーネスに宿る

プロンプトは安全な振る舞いを立ち上げ、コードがそれを強制する。四つの原則はいずれも消費者向け
エージェントとマーチャント向けエージェントの双方に適用される。

1. **モデルは用意し、人またはポリシーが適用する。** どのエージェントツールも直接お金を動かしたり
   事業状態を変えたりしない。注文確定、決済、返金、価格変更、キャンペーンはすべて既存の承認フローを
   通じた下流の承認を要する。
2. **書き込みと描画はサーバー発行の ID しか受け付けない。** セッションごとにサーバー発行 ID の
   インベントリを保持する。エージェントは幻覚した ID、ユーザーが貼り付けた ID、データプレーン由来の
   ID を使えない。提示ツールはサーバーが供給したレコードだけを描画する。
3. **上限のある取引は繰り返し要求にも耐える。** リクエストではなく結果状態に対して強制する。並列
   呼び出しが上限を積み上げないよう、カートへの書き込みをセッション単位で直列化する。マーチャント側の
   変更 — 価格変動の上限、割引の深さ、予算 — にも同じ論理を適用する。
4. **サードパーティのコンテンツはサニタイズする。** 出品情報、レビュー、ポリシー、出品者メッセージ、
   保存されたメモリなど、信頼できない入力はすべてモデルに届く前にサニタイザーを通す。制御文字を除去
   し、フェンスマーカーの模倣を取り除き、会話やツール呼び出しの模倣を無力化し、サイズを制限する。
   プロンプトには対になる指示を置く。フェンス内のテキストは報告の対象であって、決して実行の対象では
   ない。

### Eval: 非決定的なシステムを出荷する

**会話シミュレーションではなくスナップショットテスト。** テスト状態を直接構築し — システムプロンプト、
ツール、messages 配列 — テスト用のユーザーメッセージを追加してエージェントを実行し、最終状態と応答を
採点する。*「シミュレートされたユーザーによる eval は……測定の道具としては貧弱だ」* — 相互作用の
複雑さゆえに、より大きなサンプルが必要になるからだ。それらはカバレッジの発見に使い、見つかったものを
スナップショットのケースに変換する。

**厳しい条件をテストする。** 多くのスイートはきれいな初期状態のケースに偏っている。*「一定の割合は、
長く、雑然とした、あるいは矛盾した履歴から始まるようにせよ。」* 創発的な失敗はそこに現れる。

**カバレッジ。** 中核リクエスト、コンテキスト依存リクエスト、安全性とブランドのケース、インター
フェースの評価、そして隣接する二つの能力が同時に必要で両方を採点するマルチ能力リクエスト。

**プラクティス。** Product、Legal、Ops、Care、Category の各分野の専門家と組む。最も価値の高いケースは
本番の実際の失敗から来る。ユーザーフローごとに 50〜100 ケースから始める。ケース生成と敵対的バリアント
には Claude Code を使う。

### 大きな組織で出荷する

1. **オーナーシップはシステムに従う。** 各スキルと各ツールには単一のオーナーチームがあり、共有
   プロンプトにはプラットフォームレベルのオーナーとドメインオーナーが付く。スキルの追加には肯定・
   否定・境界のテストケースを添える。
2. **変更はケースとともに出荷し、CI は選別したスイートを走らせる。** CI セットは、中核となる高トラ
   フィックのケース、安全性ケースのすべて、そして変更が触れるケースから構成する。スキルなら自分の
   ケースと隣接スキルの境界ケース。ツールならそれを呼ぶすべてのケース。共有プロンプトならフル
   スイート。
3. **エージェントをリリースカレンダーに載せる。** 単一のデプロイ単位なので、悪い変更は全ユーザーに
   同時に届く。プロンプトとスキルの変更はカナリアロールアウト、デプロイなしで無効化できるスイッチ、
   繁忙期前のフリーズ。

## 第 4 部 — 変わらないもの

> この記事が述べていることの大半はモデルの話ではない。ツールはすでに運用しているシステムを呼び、
> スキルはすでに従っている手順を符号化し、eval はテストとして書かれた製品要件定義書である。

この先には音声インターフェース、値下がりの監視のような能動的なエージェントの振る舞い、そして同じ
用意・承認・出所の枠組みのもとでサードパーティのエージェントにツールを開放することがある。
